⏺ You chose swipe-arms/tap-confirms. Here's the design — it's small, since only
  the UI layer is missing.

  Architecture. No new data or repo code. ThreadRepository.deleteThread(id)
  already does the server-first DELETE, 404 tolerance, run cancellation, and
  Room removal.

  - ViewModel (ThreadsViewModel): add ThreadsEvent.ArmDelete(id),
    ThreadsEvent.ConfirmDelete(id), ThreadsEvent.CancelDelete. Hold
    armedDeleteId: String? and deleteErrorId/message in a MutableStateFlow
    folded into the existing combine. Arming starts a cancellable 3s disarm job
    — the exact confirmJob pattern from ConfigViewModel:151-164. Confirm calls
    repo.deleteThread; on false, set the inline error instead of removing the
    row (the row vanishes on its own via observeThreads when it succeeds).
  - UI (ThreadList.kt): wrap ThreadRow in a horizontal drag that arms on a left
    swipe past a threshold and snaps back — no persistent offset state, so the
    list stays keyed and simple. Armed state re-renders the row's meta line as
    tap to delete in the error colour, and the row's onClick routes to confirm
    instead of open. Error state renders delete failed · <reason> on the meta
    line.
  - Safety: a running session arms the same way but the repo already cancels its
    run; no special-casing.

  Testing. ThreadsViewModelTest via the existing VmHarness + Turbine: arm→state
  shows armed; 3s tick→disarms; confirm→row gone; confirm with
  FakeHermesClient.deleteSessionResult = Err(Network)→row stays, error surfaces.

⏺ Draft PR opened: https://github.com/liquidx/liquidx-leman-android/pull/2

  What I checked: full unit suite (187 tests, 0 failures, including 7 new delete
  cases that all genuinely ran — verified in the XML report), and assembleDebug
  compiles clean.

  What I found and what it changed: the entire network and repository layer
  already existed — HermesClient.deleteSession (DELETE /api/sessions/{id}) and
  ThreadRepository.deleteThread, which is server-first, treats 404 as
  already-gone, cancels active runs, and removes the Room row with turns
  cascading. Both were called from nowhere. So this was a UI-only job, much
  smaller than the ask implied.

  One judgment call worth flagging: you picked swipe-arms/tap-confirms, and I
  want to be explicit about why the conventional alternative was the wrong fit
  rather than just "off-brand". Material's full-swipe-plus-undo would show a
  snackbar offering an Undo the API cannot honour — the session is gone
