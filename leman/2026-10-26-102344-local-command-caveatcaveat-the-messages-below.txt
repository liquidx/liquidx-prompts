⏺ Root cause found. Here's the full picture.

  Why the cursor jumps

  The agent name box is a plain string-based BasicTextField (Inputs.kt:108)
  whose value round-trips through the ViewModel asynchronously, and Compose's
  value/onValueChange text field contract requires that round trip to be
  synchronous. The path per keystroke is:

  1. You type a character. The text field's internal buffer (its EditProcessor)
     shows it immediately and advances the cursor.
  2. onValueChange fires ConfigEvent.SetAgentName, which sets the agentNameInput
     MutableStateFlow (ConfigViewModel.kt:140) and also launches a DataStore
     write.
  3. The value the field actually renders comes back via combine(...six 
     flows...).stateIn(viewModelScope, ...) (ConfigViewModel.kt:84-115),
     collected with collectAsStateWithLifecycle in LemanNavHost.kt:180.

  That step 3 is the bug. A MutableStateFlow write does not propagate
  synchronously through combine/stateIn — it needs at least one coroutine
  dispatch, and then a recomposition frame. If you type quickly, the field's
  internal buffer is already at "abcde" while the value arriving from the state
  flow is still "abc". The string-overload BasicTextField treats the external
  value as truth, resets its buffer to the stale string, and re-derives the
  selection — which is exactly the "cursor resets and lands one or two
  characters off" you're seeing. This is a documented failure mode of the value:
  String TextField API: the new value must be reflected back in the same
  composition pass, and any Flow/ViewModel hop breaks that under fast typing.

  Two aggravating details:

  - The uncommitted fix in the working tree helped but can't fully work. The
    agentNameInput echo (the diff comment "Echo synchronously so the text field
    never sees a stale round-trip through DataStore") removed the DataStore
    round trip from the loop, shrinking the lag from "disk write + read" to "one
    dispatch + one frame" — so it misbehaves less often now, but the loop is
    still async, so fast typing still races it.
  - Every keystroke also writes to DataStore (update { it.copy(agentName = 
    event.name) }), so the settings flow re-emits per character too, doubling
    combine emissions (and doing a disk write per char). Since agentNameInput
    stays non-null and wins in the combine, this no longer resets the text —
    it's just churn.

  The server-url and api-key fields have the identical architecture, so they
  carry the same latent bug — it's probably just less visible because those are
  usually pasted rather than typed.

  How to actually fix it

  The field's live text needs a source of truth that updates synchronously with
  typing. Two clean options:

  1. Snapshot state in the ViewModel — hold the input as var agentNameInput by 
     mutableStateOf(...) (Compose snapshot state, not a StateFlow), update it
     directly in onEvent, and have the screen read it directly. Recomposition
     then sees the new value in the same frame, no coroutine hop. Persist to
     DataStore on the side (ideally debounced or on focus-loss/submit rather
     than per keystroke).
  2. Migrate PromptField to the newer BasicTextField(state = TextFieldState) API
     — the field owns its buffer, so the async-feedback problem disappears by
     construction, and the ViewModel just observes changes. This is the
     direction Google recommends and would fix all three fields at once.

  I recommend option 2 for a durable fix (it also drops the per-keystroke
  DataStore write naturally, saving on submit/change instead). Since you asked
  for the diagnosis, I've stopped here — say the word and I'll implement it.

  What changed

  Every text field in the app now uses the TextFieldState-based BasicTextField
  API, where the field owns its text buffer. The cursor bug is now impossible by
  construction — nothing writes the value back into the field per keystroke, so
  there is no async round-trip to clobber the cursor.

  The components (Inputs.kt, ThreadView.kt): PromptField and Composer take a
  TextFieldState instead of value/onValueChange, with a doc comment explaining
  why callers must not echo text back. ⏎ submit moved from KeyboardActions to
  the equivalent onKeyboardAction.

  The two ViewModels that had the bug:
  - ConfigViewModel now owns serverUrlState, apiKeyState, and agentNameState.
    They're seeded once from DataStore when settings first load; agent-name
    edits are persisted by observing the field with snapshotFlow (the pattern
    from the official Compose docs). The
    SetServerUrlInput/SetApiKeyInput/SetAgentName events and the mirror fields
    in ConfigUiState are gone. Saving the URL normalizes it back into the field;
    editing a URL that failed validation clears the error (guarded against a
    queued edit-notification wiping a fresh error — that subtlety is what the
    old event-based flow got for free, and it's covered by a test).
  - NewThreadViewModel (which had the identical latent bug) owns textState;
    Start reads it directly and the "start thread" button enables reactively off
    the field text.

  Locally-stated fields (threads filter, thread composer, debug screens) moved
  to rememberTextFieldState — the filter forwards changes to the ViewModel via
  snapshotFlow, and the composer still clears on send and survives rotation
  (rememberTextFieldState saves state internally, replacing the old
  rememberSaveable).

  Tests: written first (watched them fail on the missing API, then pass). New
  coverage includes agent-name seeding from stored settings, fast-typing
  persistence without the field ever being rewritten (the regression that
  started this), api-key clearing after save, and error-clearing on URL edit.
  The one golden that differed did so because the test previously injected
  "juno" via UiState — it now seeds the field the way production does, and the
  goldens verify unchanged.

  want a physical confirmation you can run the app on the emulator and type into
  the agent name field — happy to do either.
