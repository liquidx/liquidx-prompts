⏺ Good — I now have the full picture. Here's the grounded answer.

  The core constraint

  Everything hinges on one fact: your backend can't initiate contact with the 
  app today. Auth is pure client-pull (a static bearer key, no device
  registration), the gateway exposes no global push stream — only per-run SSE
  while a chat is in flight (docs/spec/02-server-api.md:251: "no global SSE /
  server push") — and there's no server code in this repo to change that. The
  client side is equally bare: no FCM, no google-services.json, no
  NotificationManager, no WorkManager, only INTERNET + USE_BIOMETRIC in the
  manifest. The specs already flag push as deferred "needs gateway push support"
  (docs/spec/01-architecture.md:122).

  So the real question isn't "notifications vs. background sync" — it's "can 
  something wake the app when it's closed, and who initiates it?" There are
  three answers.

  Option A — Real server push (FCM)

  The gold standard: instant, battery-cheap, works when the app is killed.

  - Client: add Firebase Messaging + google-services.json, a
    FirebaseMessagingService, POST_NOTIFICATIONS permission, register the FCM
    token on launch, and send it to the gateway.
  - Server: the gateway must (1) store per-device FCM tokens against your key
    and (2) emit an FCM push when a new message lands (including sessions
    created by cron or other clients — which is the actual reason you'd want
    notifications).
  - Blocker: step 2 doesn't exist and you don't own the gateway code. Dead end 
    unless the gateway adds a push/webhook capability. Worth confirming — GET 
    /v1/capabilities returns the full feature-flag map (per the Hermes
    contract); check it for any webhook/push/notification flag before ruling
    this out. I can probe it if you want.

  Option B — Background self-polling (WorkManager) — the only no-backend path

  Since the server can't push, the app wakes itself, calls GET /api/sessions,
  diffs against Room, and posts a local notification for anything new.

  - Yes, this is "background sync" — and it's the honest answer to your
    question: with today's backend, background sync is the only way, because
    notifications need a wake-up and the server can't provide one.
  - Reuses almost everything: SessionSyncer already change-detects on the
    server's last_active, and the leman://thread/{id} deep link already exists
    for tap-through (it's even commented "notifications and the debug panel").
  - Cost: WorkManager's periodic floor is 15 minutes, and Doze batches it
    further — so this is "within ~15+ min," never real-time. Fine for "an agent
    finished a long run"; poor for chat-like immediacy.

  Option C — A thin relay you own (best real-time path, realistically)

  Stand up a small service you control that holds the gateway relationship and
  bridges to FCM: it polls (or subscribes to) api.gent.ino.ink, and fans out FCM
  pushes to registered devices. This converts Option A's "I can't edit the
  gateway" problem into a ~100-line piece of infra you can edit — giving you
  true real-time push without waiting on Nous to add it. Costs you a deployed
  service + a token registry.

  Recommendation

  ┌──────────────────┬─────────┬──────────────────┬─────────┬───────────────┐
  │                  │ Latency │   Backend work   │ Battery │  Works when   │
  │                  │         │                  │         │    killed     │
  ├──────────────────┼─────────┼──────────────────┼─────────┼───────────────┤
  │ A. Gateway FCM   │ instant │ blocked (not     │ ✅      │ ✅            │
  │                  │         │ yours)           │         │               │
  ├──────────────────┼─────────┼──────────────────┼─────────┼───────────────┤
  │ B. WorkManager   │ ~15+    │ none             │ ⚠️ Doze │ ✅            │
  │ poll             │ min     │                  │         │               │
  ├──────────────────┼─────────┼──────────────────┼─────────┼───────────────┤
  │ C. Relay → FCM   │ instant │ small service    │ ✅      │ ✅            │
  │                  │         │ you own          │         │               │
  └──────────────────┴─────────┴──────────────────┴─────────┴───────────────┘

  Ship B first — it's self-contained, reuses your sync layer, and needs no one
  else. Treat C as the upgrade if the 15-minute latency feels bad. A only
  becomes real if /v1/capabilities shows a push flag.

  Regardless of path, the client-side pieces are the same and small: a
  notification channel, the POST_NOTIFICATIONS runtime prompt (always required
  at your minSdk 34), diff-to-notification logic, and the per-thread "notify on:
  needs me / everything" control that's already in your design mockups
  (docs/design/screens.dc.html).

  code?

⏺ This is exactly the context I needed. The unread flag in SessionSyncer is
  close to a notification signal but not quite — it deliberately marks brand-new
  rows read to suppress the first-sync flood, which would also swallow
  genuinely-new cron sessions. So notifications need their own signal derived
  from the sync, not the unread flag. That shaped the design below.

  Here's the full client design. I've broken it into sections — tell me if any
  part looks wrong and I'll revise before writing the spec.

  1. Architecture & data flow

  FCM data message ──▶ LemanMessagingService.onMessageReceived()
                          └▶ enqueue EXPEDITED SyncNotifyWorker
                                └▶ threadRepository.syncForNotifications()   
  (reuses SessionSyncer)
                                      └▶ returns List<SyncChange>
                                └▶ if app NOT foreground:
                                      MessageNotifier.post(changes)  ──▶ tap ▶ 
  leman://thread/{id}

  App start / onNewToken / toggle-on ──▶ DeviceRegistrar
                                           └▶ HermesClient.registerDevice(token,
  deviceId)
                                              POST {serverUrl}/api/devices  
  (resilient no-op if 404/unset)

  Two independent flows: inbound (push → sync → notify) and outbound (token →
  register). The existing 30s foreground SyncScheduler is untouched and posts no
  notifications — notifications are strictly a background/push concern, so the
  user isn't buzzed while actively in the app.

  Does this look right so far?

  2. The notification signal (the subtle part)

  I'll extend SessionSyncer.syncOnce() with an optional collect: ((SyncChange) 
  -> Unit)? callback (foreground path passes null, so its behavior is
  byte-for-byte unchanged). For each thread the syncer rebuilds (i.e. passed the
  serverLastActive change check), it reports a SyncChange{ threadId, title, 
  preview, isNewSession } when the newest user/agent turn is an agent turn.

  That rule naturally gives you exactly what you picked in scope:
  - new assistant turn from cron/another client → notify
  - a reply to your own message that completed while the app was backgrounded
    (stream dropped, no foreground recovery) → notify
  - your own just-sent user turn (newest turn is user) → skip
  - a cron session with only a [IMPORTANT:/system preamble and no reply yet
    (newest is system) → skip

  ThreadRepository gets suspend fun syncForNotifications(): 
  ApiResult<List<SyncChange>>.

  Two guards on top of the raw signal:
  - First-sync flood suppression: a persisted hasSeededSync flag (DataStore).
    Until the first successful full sync completes, the worker posts nothing and
    just sets the flag — otherwise a fresh install would fire dozens of
    notifications.
  - Dedup: a persisted Map<threadId, lastNotifiedServerActive> (DataStore). We
    only notify if the thread's serverLastActive is newer than what we last
    notified — so repeated pushes / 15-min retries for the same reply don't
    re-buzz. (DataStore rather than a new Room column to avoid a schema
    migration for v1.)

  Look right?

❯ The API documentation is here:                                                
                                                                                
  # Protocol                                                                    
                                                                                
  Wire contract for the notification bridge. Three interfaces:                  
                                                                                
  1. **Bridge ← phone** — device registration (public, via Caddy)               
  2. **Bridge → Hermes** — the poll (localhost)                                 
  3. **Bridge → FCM → phone** — the notification payload                        
                                                                                
  Design rationale lives in [spec.md](spec.md).                                 
                                                                                
  ---                                                                           
                                                                                
  ## 1. Bridge ← phone                                                          
                                                                                
  Public surface, reached at `https://api.gent.ino.ink/notify/*`. Caddy strips  
  nothing —                                                                     
  the bridge sees the full `/notify/...` path.                                  
                                                                                
  Auth on every endpoint except health: `Authorization: Bearer                  
  <HERMES_API_KEY>` — the same                                                  
  static token the app already holds for the gateway. A missing or wrong key    
  returns `401`                                                                 
  with the same OpenAI-style envelope the gateway uses, so the app's existing   
  error                                                                         
  handling applies unchanged:                                                   
                                                                                
  ```json                                                                       
  {"error":{"message":"Invalid API                                              
  key","type":"invalid_request_error","code":"invalid_api_key"}}                
  ```                                                                           
                                                                                
  ### `POST /notify/v1/devices`                                                 
                                                                                
  Register or update a device. Idempotent upsert keyed on `device_id`.          
                                                                                
  ```http                                                                       
  POST /notify/v1/devices                                                       
  Authorization: Bearer <HERMES_API_KEY>                                        
  Content-Type: application/json                                                
  ```                                                                           
                                                                                
  ```json                                                                       
  {                                                                             
    "device_id": "a3f21c9e8b7d4506",                                            
    "fcm_token": "e7Kx…:APA91bH…"                                               
  }                                                                             
  ```                                                                           
                                                                                
  `device_id` is a stable app-generated identifier (an install ID, not a        
  hardware ID),                                                                 
  1–128 chars. `fcm_token` is the current FCM registration token.               
                                                                                
  **200**                                                                       
                                                                                
  ```json                                                                       
  {"object": "notify.device", "device_id": "a3f21c9e8b7d4506", "registered":    
  true}                                                                         
  ```                                                                           
                                                                                
  **422** on a missing or over-long field, with FastAPI's standard validation   
  error body                                                                    
  (`{"detail": [...]}`). This differs from the `401` envelope above because it  
  signals a                                                                     
  malformed request, not an auth condition the app needs to branch on at        
  runtime.                                                                      
                                                                                
  The app calls this on first launch, on every `onNewToken`, and whenever the   
  server URL or                                                                 
  API key changes. Repeat calls with the same `device_id` and a rotated token   
  replace the                                                                   
  token and refresh `last_seen_at` — tokens rotate on reinstall, restore, and   
  app-data                                                                      
  clear, so this path is routine rather than exceptional.                       
                                                                                
  ### `DELETE /notify/v1/devices/{device_id}`                                   
                                                                                
  Deregister. Used on sign-out or when notifications are turned off in-app.     
                                                                                
  **200**                                                                       
                                                                                
  ```json                                                                       
  {"object": "notify.device.deleted", "device_id": "a3f21c9e8b7d4506",          
  "deleted": true}                                                              
  ```                                                                           
                                                                                
  **404** if unknown — safe to ignore; the desired state is already true.       
                                                                                
  ### `GET /notify/health`                                                      
                                                                                
  Unauthenticated liveness probe.                                               
                                                                                
  ```json                                                                       
  {                                                                             
    "status": "ok",                                                             
    "gateway": "reachable",                                                     
    "last_poll_at": 1784378096.4,                                               
    "devices": 1,                                                               
    "firebase": "ok"                                                            
  }                                                                             
  ```                                                                           
                                                                                
  `gateway` is                                                                  
  ──── (128 lines hidden) ───────────────────────────────────────────────────── 
  ingle                                                                         
  pending message rather than a stack. The app mirrors this with `tag =         
  session_id` on the                                                            
  posted notification, so a later turn replaces the earlier notification in the 
  tray.                                                                         
                                                                                
  ### Content in the payload                                                    
                                                                                
  `title`/`preview` are included so the notification is useful without          
  connectivity at                                                               
  receipt time — a pure invalidation signal degrades to a content-free alert,   
  or none at                                                                    
  all, exactly when the phone is offline or dozing.                             
                                                                                
  The tradeoff: this content rests on Google's servers rather than only         
  transiting them.                                                              
  Both fields already exist on the session list response, so producing them is  
  free, and                                                                     
  `INCLUDE_PREVIEW=false` reverts to pure invalidation.                         
                                                                                
  ### Token lifecycle                                                           
                                                                                
  The bridge classifies `messaging.send()` failures by the SDK **exception      
  type**, not by                                                                
  `.code`. The `.code` on these exceptions is a generic platform string, not    
  the raw FCM                                                                   
  error name — e.g. `UnregisteredError.code` is `NOT_FOUND` and                 
  `SenderIdMismatchError.code`                                                  
  is `PERMISSION_DENIED`. Matching on those generic codes would be unsafe:      
  `PERMISSION_DENIED`                                                           
  is also what a misconfigured *service account* produces (pruning on it would  
  wipe every                                                                    
  device row the first time credentials break), and `INVALID_ARGUMENT` fires    
  for a malformed                                                               
  *payload* — our own bug — as readily as for a bad token.                      
                                                                                
  | SDK exception (`firebase_admin.messaging` / `.exceptions`) | Action |       
  |---|---|                                                                     
  | `UnregisteredError` | Delete the device row — app uninstalled or token      
  expired. |                                                                    
  | `SenderIdMismatchError` | Delete the device row — token belongs to another  
  Firebase project. |                                                           
  | `InvalidArgumentError` | Log at error level, no delete — usually a bug in   
  the message we built. |                                                       
  | `QuotaExceededError`, `UnavailableError`, `InternalError`, etc. | Log and   
  drop. No retry; the app's sync backstops. |                                   
                                                                                
  Pruning only on the first two is what keeps the `devices` table from filling  
  with tokens                                                                   
  that can never receive anything, without risking a mass-deletion the first    
  time something                                                                
  else (credentials, payload) is actually broken.                               
                                                                                
  ### Delivery expectations                                                     
                                                                                
  High-priority data messages wake the app, but delivery is not guaranteed or   
  instant:                                                                      
  Doze, App Standby buckets, and FCM's data-message quotas can delay or drop    
  them. A                                                                       
  force-stopped app receives nothing until next launch.                         
                                                                                
  This is acceptable because push is an optimization over the app's existing    
  pull sync, not                                                                
  the delivery mechanism — see                                                  
  [spec.md](spec.md#delivery-is-best-effort-by-design). The app                 
  must never treat a notification as the only path by which a message can       
  arrive.
