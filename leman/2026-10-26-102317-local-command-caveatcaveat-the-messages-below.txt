⏺ Short answer: not with the current gateway — there's nothing to fetch them 
  from. I re-verified this against the live gateway (still version 0.18.0) just
  now to be sure.

  The reason is architectural: the Hermes gateway is a stateless run-runner with
  no server-side conversation store. The app carries the full message history
  in each request's input, and Room on the device is the system of record for
  threads — not a cache of anything remote. Threads started from another client
  (CLI, web, etc.) live only in that client's storage, and the gateway offers no
  way to enumerate them:

  - GET /v1/runs (with or without a session_id filter) → 405
  - /v1/sessions and /v1/threads → 404
  - session_id only groups runs; it doesn't create retrievable server-side
    history

  There are two partial escape hatches, in case one fits what you actually want:

  1. Import by run ID. GET /v1/runs/{id} returns the full run object, and GET 
     /v1/runs/{id}/events replays the complete event history for completed runs.
     So if you know a run_id (e.g., pasted from another client), the app could
     reconstruct that exchange into a local thread. This would be an app-side
     "import run" feature — feasible today, but it requires the ID; there's no
     discovery.
  2. Change the gateway or add a shared store. True cross-client thread
     visibility needs either the gateway to grow a list/persistence API, or all
     clients to sync through a common backend (which the app's Room-primary
     design in docs/spec/03-sync-and-cache.md doesn't currently assume). That's
     a server-side project, not an app change.

  If the underlying goal is "I use another Hermes client and want those
  conversations on my phone," option 1 (paste-a-run-ID import) is the only thing
  buildable right now — happy to spec or implement it if you want.
