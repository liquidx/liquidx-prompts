  This feature already exists and is fully wired up. The architecture you're
  describing — local cache, no blocking fetch on startup, merge
  server-with-cache on startup and periodically — is already the implemented
  design. Here are the four pieces:

  1. Durable local cache — LemanDatabase (data/local/LemanDatabase.kt) is an
     on-disk Room DB (leman.db) holding ThreadEntity + TurnEntity. It survives
     process restarts (fallbackToDestructiveMigration only drops on a
     schema-version bump, not on relaunch). A comment states the intent
     explicitly: "Room is a cache of the gateway's session store."
  2. No blocking fetch on startup — the UI observes Room, not the network.
     ThreadsViewModel (ui/threads/ThreadsViewModel.kt:76) builds its state from
     repo.observeThreads(), a Room Flow. So on cold start the cached sessions
     render immediately; the network is never on the critical path.
  3. Merge on startup + periodically — SyncScheduler
     (data/repo/SyncScheduler.kt) fires a sync the instant the gateway goes
     Online on foreground, then again every 30s while foregrounded
     (backgrounding cancels). Each tick calls SessionSyncer.syncOnce()
     (data/repo/SessionSyncer.kt), which is a genuine merge, not a replace: it
     preserves local-only sidecar state (pinned / unread / agentName /
     agentGlyph), carries unsynced local turns across the rebuild, skips threads
     with an in-flight run, and change-detects on the server's last_active so
     unchanged threads aren't touched.

  So the behavior "merge what the server gives us with the cached client on
  startup and periodically when the app is open" is already what runs today.

  Given that, I don't want to build a redundant second copy. What's the actual
  gap you're seeing?

  It's already documented

  docs/spec/03-sync-and-cache.md is the spec for exactly this. It states the
  governing principle ("Room is a cache, not primary storage"), diagrams the
  SessionSyncer → Room → Flow → ViewModel data flow, and has dedicated sections
  for Sync triggers (foreground immediate + 30s loop + post-send), Sidecar 
  preservation, and Offline behavior. There's also a matching design doc at
  docs/superpowers/specs/2026-07-17-session-sync-design.md.

  One deliberate non-goal (in case it's what you actually want)

  The spec explicitly rules out one thing you might be imagining: there is no 
  background sync — "Backgrounding cancels the loop outright — no sync while the
  app isn't visible, no WorkManager, no push." So the cache only refreshes
